# GNS3 API drift: 2.2.52 docs vs a live 2.2.61 server

The client was written from the GNS3 server 2.2.52 controller API docs (<https://gns3-server.readthedocs.io/en/stable/endpoints.html>). On 2026-10-07 it was run against a live GNS3 2.2.61 server on Windows (`Invoke-Build TestAcc -AutoStart`, manual-check-list items 1.1 to 1.5, and the fixture re-recording in `internal/client/testdata`). This page lists every place where the live server did something the docs don't say, and which behaviour the client now follows. Some entries are probably gaps in the docs rather than changes between 2.2.52 and 2.2.61; no 2.2.52 server was run to tell them apart.

This page is written by hand. It is not generated by tfplugindocs and is not part of the registry docs.

## Changes the provider had to make

### VPCS `startup_script` cannot be updated through node PUT

Endpoint: `PUT /v2/projects/{project_id}/nodes/{node_id}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeid.html)).

- **Docs:** `properties` is a free-form object of emulator properties, forwarded to the compute. The node create sample sends `"properties": {"startup_script": "echo test"}`, so the same key looks updatable.
- **2.2.61:** `POST .../nodes` accepts `startup_script`, writes it to `startup.vpc` in the node directory and keeps a copy in the controller's node record. Every later PUT, even a rename with no `properties`, forwards that cached copy to `PUT /v2/compute/projects/{project_id}/vpcs/nodes/{node_id}`. The compute schema rejects it, so the PUT fails:

  ```
  HTTP 400: Bad request http://127.0.0.1:3080/v2/compute/projects/.../vpcs/nodes/... "JSON schema error with API request '...' and JSON data
  '{'startup_script': 'set pcname tfacc', 'name': 'PC2-renamed', 'console': 5002, 'console_type': 'telnet'}':
  Additional properties are not allowed ('startup_script' was unexpected)"
  ```

  The cached copy also goes stale: after `POST .../files/startup.vpc`, `GET .../nodes/{node_id}` still reports the old `startup_script`, even after a close and reopen.
- **Client now:** `gns3_node` treats `startup_script` on `vpcs` nodes as file-backed (`fileProperties` in `internal/provider/node_resource.go`). It never sends the key in `properties`. On create and update it writes the value with `POST .../nodes/{node_id}/files/startup.vpc`, and on read it takes the value from `GET .../files/startup.vpc`. `TestAccNodeResource` step 2 renames the node and changes the script, and checks the file content.

### Project DELETE races the emulator process on Windows

Endpoint: `DELETE /v2/projects/{project_id}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/project/projectsprojectid.html)).

- **Docs:** 204, or 404 when the project doesn't exist.
- **2.2.61 on Windows:** `DELETE .../nodes/{node_id}` returns 204 while a started node's `vpcs.exe` is still exiting. If the project delete arrives within the same half second, it fails:

  ```
  HTTP 409: Cannot delete project directory C:\...\projects\<id>: [WinError 32] The process cannot access the file
  because it is being used by another process: '...\project-files\vpcs\<node_id>\vpcs.log'
  ```

  In the first acceptance run this left two projects behind. When the same deletes were sent by hand, one after another, it did not happen.
- **Client now:** the `gns3_project` delete retries that one 409 (message contains "Cannot delete project directory") with backoff for up to 15 s (`deleteProjectRetrying` in `internal/provider/project_resource.go`). Every other error is reported at once. In items 1.4 and 1.5 the server log shows one 409 followed by a 204.

## Differences the client tolerates without changes

| Endpoint | 2.2.52 docs | 2.2.61 live | Client follows |
|---|---|---|---|
| `GET /v2/projects/{project_id}/nodes/{node_id}/files/{path}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeidfilespath.html)) | 204 "Instance reloaded" (copied from another endpoint) | 200, body is the raw file, `Content-Type: application/octet-stream`; 404 `{"message": "GET /projects/<id>/files/project-files/vpcs/<node_id>/<path> not found", "status": 404}` when missing | live: `ReadNodeFile` returns the body; 404 is `IsNotFound` |
| `POST /v2/projects/{project_id}/nodes/{node_id}/files/{path}` (same page) | 204 "Instance reloaded" | 201, empty body | live: any 2xx |
| `POST /v2/projects/{project_id}/nodes/{node_id}/start` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeidstart.html)) | 200 with the node object (status started implied) | 200, but the body is the node as it was before the start: `"status": "stopped"`. A GET immediately after says `"started"` (5 of 5 tries, about 400 ms after the call) | live: the provider ignores the start response and re-reads with GET |
| Link object (`GET`/`POST`/`PUT .../links...`) | `nodes[].label` with `text`, `x`, `y`; no `link_style` | adds `link_style: {}`; `nodes[].label` is `{style, text}` (`text` is `"0/0"`) | both: `client.Link` doesn't decode labels or style |
| `PUT .../links/{link_id}` | 201 | 201 (matches the docs; noted because PUT returning 201 is unusual) | live |
| Node created from a template (`POST /v2/projects/{project_id}/templates/{template_id}`) | sample node has `properties.startup_script` | VPCS from the built-in template: `"properties": {}`; `command_line` and `node_directory` are filled in rather than null | live: `properties` keys are compared only when configured |
| `POST /v2/projects` duplicate name | 409 "Project already created" (wording assumed in the 0.1.0 fixture: `Project 'test' already exists`) | 409 `Project "test" already exists` | live (the message is passed through unchanged) |
| `GET /v2/templates` | sample lists 5 built-ins plus a user qemu template | 7 built-ins on Windows: Cloud, NAT, VPCS, Ethernet switch, Ethernet hub, Frame Relay switch, ATM switch | live: `gns3_template` looks up by name or ID, never by position |
| `GET /v2/computes` | `capabilities.node_types` assumed | on Windows: `cloud, ethernet_hub, ethernet_switch, nat, vpcs, virtualbox, dynamips, frame_relay_switch, atm_switch, qemu, vmware, traceng` (no `docker`, `iou`) | both: not decoded |

## Confirmed as documented

- `PUT /v2/projects/{project_id}/nodes/{node_id}` accepts the docs-shaped body (`compute_id`, `name`, `node_type` plus the changed fields) on any node that has no cached `startup_script`. The error echo leaves out `compute_id` and `node_type`, but they are accepted.
- `POST /v2/projects/{project_id}/close` returns 204 with an empty body; `POST .../open` returns 201 with the project.
- Creating a node from a template with `"name": "PC1"` keeps the name `PC1` (no server-side rename).
- `POST .../links` with both ends on the same node returns 409 `Cannot connect to itself` (recorded against a built-in Ethernet switch; on a one-port VPCS node the server answers 404 first, because port 3 doesn't exist).

## Server setup notes (not API drift)

- On Windows the built-in Ethernet hub and switch run on Dynamips. A `gns3server` started with its own config needs `[Dynamips] dynamips_path` or node creation fails with 409 "Could not find Dynamips". `Invoke-Build Gns3Start` sets it.
- 2.2.61 installs uBridge as `ubridge\ubridge.exe`. An upgraded install can still have a 2022 `ubridge.exe` in the install root, so `Gns3Start` prefers the subfolder.
