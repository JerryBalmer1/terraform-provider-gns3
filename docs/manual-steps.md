# Looking at a scenario in the GNS3 GUI

Up: [README](../README.md)

See also: [Scenario tests](../test/scenarios/README.md), [GNS3 install record](gns3-install.md), [API drift](api-drift.md), [Emulator images](images.md)

This page lists every step it took to look at a scenario by hand, and what `Invoke-Build Gns3Range -Scenario <name> -Inspect` now does with each one. Not generated by tfplugindocs and not part of the Registry docs.

## Before: by hand

1. Start a GNS3 server (`Invoke-Build Gns3Start`, or let gns3.exe start its local one).
2. Point Terraform at the provider build (a CLI config with `dev_overrides`, or none for the Registry release).
3. `terraform -chdir=test/scenarios/<name> init -upgrade`.
4. `terraform apply`.
5. Run `checks.ps1` with the server URL and the `terraform output -json` values.
6. Open gns3.exe.
7. Make sure the GUI is connected to that server (its local server is `localhost:3080`).
8. Find the project: **File > Open project**, pick `tf-scenario-<name>`.
9. Start the nodes: **Control > Start/Resume all nodes**.
10. Open a console: right-click each node > **Console**.
11. Type the commands from the scenario README (`show ip`, `ping ...`) and read the results.
12. Judge the canvas: node positions, the cable, the link indicators.
13. Close the project or gns3.exe.
14. `terraform destroy`.
15. Delete the leftover state, so the next `Gns3Range` does not refuse with "stale state".
16. Stop the server, if the build started it.

## Now: what -Inspect and -Destroy do

| # | Step | Decision | Why |
|---|---|---|---|
| 1 | Start the server | Automate | `Gns3Range` already starts one when nothing answers. Under `-Inspect` it leaves it running and records that it started it. |
| 2 | Point Terraform at the provider | Automate | `Gns3Range` writes its own CLI config (`direct {}`, or `dev_overrides` with `-Dev`); `terraform.rc` is never touched. |
| 3 | `init -upgrade` | Automate | Same as the default run. |
| 4 | `apply` | Automate | Same as the default run. |
| 5 | Run `checks.ps1` | Automate | Same as the default run; a failure is still a FAIL row. |
| 6 | Open gns3.exe | Automate | Started with the project's `.gns3` file when GNS3 is installed here, the server is local and no gns3.exe is running (a second gns3.exe opens a second window). Otherwise the printed line says where to open the project, including the web UI address (`/static/web-ui/bundled`). |
| 7 | Connect the GUI to the server | Print as instruction | The GUI uses its own settings (`%APPDATA%\GNS3\2.2`), which the build never edits. With the defaults (local server on `localhost:3080`) it connects to the build's server; if it does not, the printed line says to use **File > Open project** or the web UI. |
| 8 | Find and open the project | Automate | Passing the `.gns3` path to gns3.exe opens it (seen on 2.2.61, 2026-10-16). |
| 9 | Start the nodes | Automate | `POST /v2/projects/{project_id}/nodes/start`, then a check that every node reports `started`. |
| 10 | Open a console | Print as instruction | One `telnet://host:port` line per node, read from the API, which the terminal makes clickable. Opening windows for every node is noisy, and the console client is Jerry's choice. |
| 11 | Type commands, read results | Must stay manual | Looking at a running lab is the point of `-Inspect`. Anything a script can assert belongs in `checks.ps1`. The commands and expected results come from the `inspect` array in `scenario.json` and are printed. |
| 12 | Judge the canvas | Must stay manual | Layout and link colours are a human judgement; the scenario README says what to expect. `-Capture` (still a stub) is the place for screenshots. |
| 13 | Close the project or gns3.exe | Must stay manual | The build never closes a GUI it does not own. After `-Destroy` deletes the project, the GUI drops it by itself (seen on 2.2.61). |
| 14 | `destroy` | Automate | `Gns3Range -Scenario <name> -Destroy`, the command printed at the end of the `-Inspect` block. |
| 15 | Clear the state | Automate | `-Destroy` checks that `terraform state list` is empty, then removes `terraform.tfstate` and its backup. |
| 16 | Stop the server | Automate | `-Destroy` stops it only when the `-Inspect` run started it and no other scenario is still inspected. A server started any other way is never stopped. |
