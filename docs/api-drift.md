# GNS3 API drift: 2.2.52 docs vs a live 2.2.61 server

Up: [README](../README.md)

See also: [Provider docs](index.md), [Emulator images](images.md), [GNS3 install record](gns3-install.md), [Looking at a scenario in the GUI](manual-steps.md)

The client was written from the GNS3 server 2.2.52 controller API docs (<https://gns3-server.readthedocs.io/en/stable/endpoints.html>). On 2026-10-07 it was run against a live GNS3 2.2.61 server on Windows (`Invoke-Build TestAcc -AutoStart`, manual-check-list items 1.1 to 1.5, and the fixture re-recording in `pkg/gns3/testdata`). This page lists every place where the live server did something the docs don't say, and which behaviour the client now follows. The image endpoints were added and checked the same way on 2026-10-15 (a server started by `Invoke-Build Gns3Start`, by hand with curl and through `TestAccImage*`). Some entries are probably gaps in the docs rather than changes between 2.2.52 and 2.2.61; no 2.2.52 server was run to tell them apart.

This page is written by hand. It is not generated by tfplugindocs and is not part of the registry docs.

## Changes the provider had to make

### VPCS `startup_script` cannot be updated through node PUT

Endpoint: `PUT /v2/projects/{project_id}/nodes/{node_id}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeid.html)).

- **Docs:** `properties` is a free-form object of emulator properties, forwarded to the compute. The node create sample sends `"properties": {"startup_script": "echo test"}`, so the same key looks updatable.
- **2.2.61:** `POST .../nodes` accepts `startup_script`, writes it to `startup.vpc` in the node directory and keeps a copy in the controller's node record. Every later PUT, even a rename with no `properties`, forwards that cached copy to `PUT /v2/compute/projects/{project_id}/vpcs/nodes/{node_id}`. The compute schema rejects it, so the PUT fails:

  ```
  HTTP 400: Bad request http://127.0.0.1:3080/v2/compute/projects/.../vpcs/nodes/... "JSON schema error with API request '...' and JSON data
  '{'startup_script': 'set pcname tfacc', 'name': 'PC2-renamed', 'console': 5002, 'console_type': 'telnet'}':
  Additional properties are not allowed ('startup_script' was unexpected)"
  ```

  The cached copy also goes stale: after `POST .../files/startup.vpc`, `GET .../nodes/{node_id}` still reports the old `startup_script`, even after a close and reopen.
- **Client now:** `gns3_node` treats `startup_script` on `vpcs` nodes as file-backed (`fileProperties` in `internal/provider/node_resource.go`). It never sends the key in `properties`. On create and update it writes the value with `POST .../nodes/{node_id}/files/startup.vpc`, and on read it takes the value from `GET .../files/startup.vpc`. `TestAccNodeResource` step 2 renames the node and changes the script, and checks the file content.

### Dynamips startup and private configs cannot be updated through node PUT

Endpoint: `PUT /v2/projects/{project_id}/nodes/{node_id}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeid.html)). Probed on 2026-10-15 against a 2.2.61 server started by `Invoke-Build Gns3Start`, with a template-less c7200 node (`"image": "tf-probe-placeholder-c7200.image"`, a 60-byte text file uploaded to the `IOS` folder for the probe). The router was never started.

- **Docs:** `properties` is forwarded to the compute; the dynamips compute create page lists `startup_config_content` and `private_config_content`.
- **2.2.61:**
  - Create works. `POST .../nodes` with both keys returns them in `properties`, and the compute writes them to `configs/i<dynamips_id>_startup-config.cfg` and `configs/i<dynamips_id>_private-config.cfg` in the node directory **with `!\n` prepended** (`"hostname R1\n"` became `"!\nhostname R1\n"`).
  - Updating them fails. A PUT with either key is rejected by the compute's dynamips update schema, and nothing changes:

    ```
    HTTP 400: Bad request http://127.0.0.1:3080/v2/compute/projects/.../dynamips/nodes/... "JSON schema error with API request '...' and JSON data
    '{'private_config_content': '! private updated\\n', 'startup_config_content': 'hostname R1-updated\\n', 'name': 'R1', 'console': 5004, 'console_type': 'telnet'}':
    Additional properties are not allowed ('startup_config_content', 'private_config_content' were unexpected)"
    ```

  - As with VPCS `startup_script`, the controller caches the keys from create and forwards them on every later PUT. A rename with no `properties` (`{"name": "R1b"}`) fails with the same 400.
  - `POST .../files/configs/i1_startup-config.cfg` writes the body exactly (no `!` prefix), `GET` returns it, and `GET .../nodes/{node_id}` keeps reporting the stale cached `startup_config_content`.
  - **Not seen:** whether Dynamips loads the rewritten file at the next start. That needs a real IOS image.
- **Client now:** `gns3_node` refuses `startup_config_content` and `private_config_content` in `properties` on `dynamips` nodes (`refusedProperties` in `internal/provider/node_resource.go`). `startup_config` writes and reads `configs/i<dynamips_id>_startup-config.cfg` through the files endpoint, with `dynamips_id` taken from the node's `properties`. The private config is not managed. `TestNodeStartupConfigDynamips` (fake) renames the node and changes the config in one update. `TestAccNodeStartupConfigDynamips` does the same against a live server, and skips when the server has no Dynamips template.

### Startup configuration per node type

Probed on 2026-10-15 against 2.2.61 on Windows, each with a throwaway project that was deleted afterwards. This is what `startup_config` on `gns3_node` follows.

| Node type | 2.2.61 | `startup_config` |
|---|---|---|
| `vpcs` | `GET .../files/startup.vpc` is 404 before anything is written. `POST` writes it exactly, and `GET` returns the same bytes. The node's `properties` stay `{}`, and a rename afterwards succeeds | supported: `startup.vpc` |
| `dynamips` | see the section above | supported: `configs/i<dynamips_id>_startup-config.cfg` |
| `qemu` | the node's `properties` (2.2.61, with `platform` `x86_64`) have no startup-config key, and `GET .../files/startup-config.cfg` is 404. The one related key is `create_config_disk`, which builds a config disk on `hdd` from the node's `config.zip` when the compute supports it (see [qemu config disk (2.2.61)](#qemu-config-disk-2261)) | refused at plan time; the error points to `properties.create_config_disk` |
| `iou`, `docker` | not probed: the Windows compute's `capabilities.node_types` has neither | refused at plan time as "not supported yet" until probed on a GNS3 VM or Linux compute |
| others (`cloud`, `nat`, switches, hubs, `traceng`, `virtualbox`, `vmware`) | not probed; no startup-config property in the docs | refused: "has no startup configuration" |

A node created from a template gets the same check at plan time, after `GET /v2/templates/{template_id}` gives `template_type`.

### qemu config disk (2.2.61)

Property: `create_config_disk` on `POST /v2/compute/projects/{project_id}/qemu/nodes` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/compute/qemu/projectsprojectidqemunodes.html)), set through `properties` on the controller node create. Files: `GET`/`POST /v2/projects/{project_id}/nodes/{node_id}/files/{path}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeidfilespath.html)). Source: `gns3server/compute/qemu/qemu_vm.py` and `gns3server/compute/qemu/__init__.py` at tag [v2.2.61](https://github.com/GNS3/gns3-server/tree/v2.2.61/gns3server/compute/qemu).

- **Docs:** "Automatically create a config disk on HDD disk interface (secondary slave)", boolean. Nothing about what goes on the disk or where it comes from.
- **Source (v2.2.61):**
  - The manager uses one fixed image name, `config.img`, in the `QEMU` images folder. At startup `_init_config_disk` unpacks the bundled resource `compute/qemu/resources/config.img.zip` there if it is missing. `config.img` is a blank disk with an MBR and one FAT partition.
  - Each node blanks its `config_disk_name` at creation (so the feature is off for that node) when `mcopy` (mtools) is not on the server's `PATH`, or when `config.img` is not in the images folder. Only a log warning says so; the API still accepts and returns `create_config_disk: true`.
  - At start (`_disk_options`), when `create_config_disk` is true and the image exists: `hdd_disk_image` is ignored, `_import_config` runs, and `<node_dir>/config.img` is attached as drive index 3 (`hdd`), `format=raw`, on `hdd_disk_interface` (or `hda_disk_interface` when that is `none`).
  - `_import_config`: the input is **`<node_dir>/config.zip`**. When it exists, the server copies the blank `config.img` to `config.img.tmp`, unpacks the zip and `mcopy`s every top-level entry to the FAT root (`::/`), then replaces `<node_dir>/config.img`. When `config.zip` is missing, an existing `<node_dir>/config.img` is reused as is, or the blank image is copied in. If `hdd_disk_image` names a `.zip` file and neither `config.zip` nor `config.img` exists, that zip is copied to `config.zip` first.
  - At stop (`stop` → `_export_config`): the server copies everything on the FAT disk back out with `mcopy` and **rewrites `config.zip`** from it. So `config.zip` holds whatever the guest saved to the disk, not what was uploaded.
  - Nothing is specific to an appliance: no `config.boot`, no cloud-init, no file names. The guest has to mount the disk and read it itself. The `vyos.gns3a` appliance in gns3-registry does not set `create_config_disk`, and a GitHub code search for `create_config_disk` in the GNS3 org on 2026-10-16 found it only in gns3-server and gns3-gui, in no appliance file.
- **2.2.61 on Windows** (probed 2026-10-16, `GET /v2/version` 2.2.61, the server already running on port 3080 from an earlier `Invoke-Build Gns3Start`, PID 150704; throwaway project `tf-probe-qemu-config-disk`, deleted afterwards):
  - The server log has `WARNING __init__.py:395 Config disk: image 'config.img' missing` at every startup. No `config.img` is in `$env:TEMP\gns3\data\images\QEMU`, and no file named `config.img*` is under `C:\Program Files\GNS3`: the Windows install ships no `config.img.zip`. `mcopy` is not on `PATH` either.
  - `POST .../nodes` with `node_type` `qemu` and `properties` `{create_config_disk: true, hda_disk_image: "empty8G.qcow2", ram: 256, platform: "x86_64"}` returns 201, and `properties.create_config_disk` comes back `true`. The log then says `WARNING qemu_vm.py:150 Config disk: 'mtools' are not installed.` No property names the config disk image.
  - The node directory (`<project>\project-files\qemu\<node_id>`) is empty after create. `GET .../files/config.img` and `GET .../files/config.zip` are 404. There is no listing: `GET .../files/` is 404.
  - `POST .../files/config.zip` with a 161-byte zip holding `config.boot` (`system { host-name tf-probe-vyos }`) returns 201 and writes `<node_dir>\config.zip`. `GET` returns the same bytes (same MD5).
  - `POST .../nodes/{node_id}/start` fails with 409 `HAXM acceleration support is not installed on this host`, so no qemu process ran. After `stop`, `config.zip` is unchanged and no `config.img` appears. Free RAM on the host was about 1.4 GB.
  - **Not seen:** a config disk being built or attached, and whether VyOS reads anything from it. On this host the feature is off (no `config.img`, no mtools), qemu can't start (no HAXM), and no VyOS image is on the server. That needs a GNS3 VM or Linux compute with mtools and KVM, and a VyOS qcow2.
- **Client now:** unchanged. `startup_config` on `qemu` is still refused at plan time.

### Project DELETE races the emulator process on Windows

Endpoint: `DELETE /v2/projects/{project_id}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/project/projectsprojectid.html)).

- **Docs:** 204, or 404 when the project doesn't exist.
- **2.2.61 on Windows:** `DELETE .../nodes/{node_id}` returns 204 while a started node's `vpcs.exe` is still exiting. If the project delete arrives within the same half second, it fails:

  ```
  HTTP 409: Cannot delete project directory C:\...\projects\<id>: [WinError 32] The process cannot access the file
  because it is being used by another process: '...\project-files\vpcs\<node_id>\vpcs.log'
  ```

  In the first acceptance run this left two projects behind. When the same deletes were sent by hand, one after another, it did not happen.
- **Client now:** the `gns3_project` delete retries that one 409 (message contains "Cannot delete project directory") with backoff for up to 15 s (`deleteProjectRetrying` in `internal/provider/project_resource.go`). Every other error is reported at once. In items 1.4 and 1.5 the server log shows one 409 followed by a 204.

### No endpoint deletes an image

Endpoints: `GET /v2/computes/{compute_id}/{emulator}/images` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/compute/sidemulatorimages.html)) and the forward route `/v2/computes/{compute_id}/{emulator}/{action}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/compute/sidemulatoraction.html)), which carries uploads to `POST /v2/compute/{emulator}/images/{filename}` on the compute ([qemu docs](https://gns3-server.readthedocs.io/en/stable/api/v2/compute/qemu/qemuimagesfilename.html)).

- **Docs:** images can be listed (GET) and uploaded or downloaded (POST/GET on `.../images/{filename}`). No DELETE is listed on either the controller or the compute pages.
- **2.2.61:** `DELETE /v2/computes/local/qemu/images/<file>` answers `405 Method Not Allowed` (`Allow: GET,OPTIONS,POST,PUT`, plain-text body). The only way to remove an image is on the compute's file system.
- **Client now:** `ImagesAPI` has no delete. `gns3_image` destroy removes the resource from state and adds the warning "GNS3 image left on the compute" with the file name, emulator, compute and path. `TestImageResource` checks that the fake still holds the file after destroy.

## Differences the client tolerates without changes

| Endpoint | 2.2.52 docs | 2.2.61 live | Client follows |
|---|---|---|---|
| `GET /v2/projects/{project_id}/nodes/{node_id}/files/{path}` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeidfilespath.html)) | 204 "Instance reloaded" (copied from another endpoint) | 200, body is the raw file, `Content-Type: application/octet-stream`; 404 `{"message": "GET /projects/<id>/files/project-files/vpcs/<node_id>/<path> not found", "status": 404}` when missing | live: `ReadNodeFile` returns the body; 404 is `IsNotFound` |
| `POST /v2/projects/{project_id}/nodes/{node_id}/files/{path}` (same page) | 204 "Instance reloaded" | 201, empty body | live: any 2xx |
| `POST /v2/projects/{project_id}/nodes/{node_id}/start` ([docs](https://gns3-server.readthedocs.io/en/stable/api/v2/controller/node/projectsprojectidnodesnodeidstart.html)) | 200 with the node object (status started implied) | 200, but the body is the node as it was before the start: `"status": "stopped"`. A GET immediately after says `"started"` (5 of 5 tries, about 400 ms after the call) | live: the provider ignores the start response and re-reads with GET |
| Link object (`GET`/`POST`/`PUT .../links...`) | `nodes[].label` with `text`, `x`, `y`; no `link_style` | adds `link_style: {}`; `nodes[].label` is `{style, text}` (`text` is `"0/0"`) | both: `gns3.Link` doesn't decode labels or style |
| `PUT .../links/{link_id}` | 201 | 201 (matches the docs; noted because PUT returning 201 is unusual) | live |
| Node created from a template (`POST /v2/projects/{project_id}/templates/{template_id}`) | sample node has `properties.startup_script` | VPCS from the built-in template: `"properties": {}`; `command_line` and `node_directory` are filled in rather than null | live: `properties` keys are compared only when configured |
| `POST /v2/projects` duplicate name | 409 "Project already created" (wording assumed in the 0.1.0 fixture: `Project 'test' already exists`) | 409 `Project "test" already exists` | live (the message is passed through unchanged) |
| `GET /v2/templates` | sample lists 5 built-ins plus a user qemu template | 7 built-ins on Windows: Cloud, NAT, VPCS, Ethernet switch, Ethernet hub, Frame Relay switch, ATM switch | live: `gns3_template` looks up by name or ID, never by position |
| `GET /v2/computes` | `capabilities.node_types` assumed | on Windows: `cloud, ethernet_hub, ethernet_switch, nat, vpcs, virtualbox, dynamips, frame_relay_switch, atm_switch, qemu, vmware, traceng` (no `docker`, `iou`) | both: not decoded |

| `POST /v2/computes/{compute_id}/{emulator}/images/{filename}` (forward route, above) | compute page: 204 "Image uploaded" | 200 with body `{}` through the controller. An existing file of the same name is overwritten without error, and its `.md5sum` cache is refreshed | live: any 2xx. `gns3_image` refuses at create to upload over a different file it did not upload |
| `GET /v2/computes/{compute_id}/{emulator}/images` | no sample; 404 "Instance doesn't exist" | 200 with `[{filename, filesize, md5sum, path}]`. `path` is relative to the emulator's folder (`QEMU`, `IOS`, `IOU`), so `sub/x.img` for a file in a subfolder, listed with `filename` `x.img`. 2.2.61 adds its own `OVMF_*.fd` and `empty*.qcow2` to `QEMU`, so a fresh server lists 16 qemu images | live: `gns3_image` matches `path` = `filename` (top of the folder); the data source matches `filename` |
| Same, `emulator` = `dynamips` | not described | lists only 32-bit big-endian ELF files. A 36-byte text file uploaded as `dynamips` was stored in `IOS` but missing from the dynamips list, and appeared in the **qemu** list with an absolute `path` (`C:/.../images/IOS/tf-probe.image`). Source: `list_images` in `gns3server/utils/images.py` (2.2 branch), which also drops ELF files from qemu, files under 7 bytes from every list, and keeps only little-endian ELF for iou | live: after an upload that isn't listed, `gns3_image` fails with "the upload succeeded but compute ... does not list ..." and names the filter |
| Same, `emulator` = `iou` or `docker`, Windows compute | iou, dynamips and qemu accepted; docker images on the compute page | the controller forwards both; the Windows compute answers 404 `{"message": "GET /iou/images not found"}` (`/docker/images` likewise; the compute's `capabilities.node_types` has neither). `foo` gives the same 404, and an unknown compute gives 404 `Compute ID nope doesn't exist` | live: errors pass through unchanged. `ListDockerImages` is tested only against a hand-written fixture |

## Confirmed as documented

- `PUT /v2/projects/{project_id}/nodes/{node_id}` accepts the docs-shaped body (`compute_id`, `name`, `node_type` plus the changed fields) on any node that has no cached `startup_script` (vpcs) or `startup_config_content`/`private_config_content` (dynamips). The error echo leaves out `compute_id` and `node_type`, but they are accepted.
- `POST /v2/projects/{project_id}/close` returns 204 with an empty body; `POST .../open` returns 201 with the project.
- Creating a node from a template with `"name": "PC1"` keeps the name `PC1` (no server-side rename).
- `POST .../links` with both ends on the same node returns 409 `Cannot connect to itself` (recorded against a built-in Ethernet switch; on a one-port VPCS node the server answers 404 first, because port 3 doesn't exist).

## Server setup notes (not API drift)

- On Windows the built-in Ethernet hub and switch run on Dynamips. A `gns3server` started with its own config needs `[Dynamips] dynamips_path` or node creation fails with 409 "Could not find Dynamips". `Invoke-Build Gns3Start` sets it.
- 2.2.61 installs uBridge as `ubridge\ubridge.exe`. An upgraded install can still have a 2022 `ubridge.exe` in the install root, so `Gns3Start` prefers the subfolder.
