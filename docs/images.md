# Emulator images for a GNS3 lab

Where GNS3 2.2 keeps emulator images, which free images suit a lab, and how `gns3_image` puts them on a compute. Researched 2026-10-15; versions and sizes move, so check each download page.
This page is written by hand. It is not generated by tfplugindocs and is not part of the registry docs.

## Where the compute keeps images

Each compute has one images folder (`images_path` under `[Server]` in `gns3_server.conf`/`.ini`) with a subfolder per emulator. `GET /v2/computes/{compute_id}/{emulator}/images` lists one subfolder, and `gns3_image` uploads into it.

| Emulator (`emulator =`) | Subfolder | Windows, local server | GNS3 VM | Server started by `Invoke-Build Gns3Start` |
|---|---|---|---|---|
| `qemu` | `QEMU` | `%USERPROFILE%\GNS3\images\QEMU` | `/opt/gns3/images/QEMU` | `$env:TEMP\gns3\data\images\QEMU` |
| `dynamips` | `IOS` | `%USERPROFILE%\GNS3\images\IOS` | `/opt/gns3/images/IOS` | `$env:TEMP\gns3\data\images\IOS` |
| `iou` | `IOU` | none: IOU runs only on Linux | `/opt/gns3/images/IOU` | none |

Sources: the default `images_path` is `~/GNS3/images` and the subfolder names come from `default_images_directory` in [gns3server/utils/images.py](https://github.com/GNS3/gns3-server/blob/2.2/gns3server/utils/images.py) (2.2 branch). On Windows that is `%USERPROFILE%\GNS3\images`, not `Documents\GNS3` (seen on the dev machine 2026-10-15). The GNS3 VM sets `images_path = /opt/gns3/images` in [provision_gns3.sh](https://github.com/GNS3/gns3-vm/blob/master/scripts/provision_gns3.sh). `Gns3Start` writes its own `images_path` (`.build.ps1`).

What the list shows (from the same `list_images`, checked against 2.2.61 where noted):

- Each file name appears once. A file in a subfolder is listed by its base name with `path` `sub/name` (seen on 2.2.61). Files from `additional_images_path` and from other emulators' folders can appear with an absolute `path`.
- `qemu` leaves out ELF executables. `dynamips` shows only 32-bit big-endian ELF files (unpacked IOS images); a non-ELF file uploaded as `dynamips` is stored but never listed (seen on 2.2.61). `iou` shows only little-endian ELF files. All three leave out files under 7 bytes.
- 2.2.61 puts its own `OVMF_*.fd` firmware and `empty*.qcow2` blank disks in `QEMU`, so a fresh server already lists 16 qemu images.

`Invoke-Build Gns3Images` prints these lists for every emulator on a compute.

### Docker is the exception

Docker images are not files in the images folder. The compute's Docker daemon pulls them when a Docker node or template is first used, and `GET /v2/computes/{compute_id}/docker/images` lists what the daemon already has (`repo:tag` names). There is no upload; `gns3_image` doesn't cover Docker. A Windows compute has no Docker support at all (the list answers 404 `GET /docker/images not found`), so Docker nodes need the GNS3 VM or a Linux server.

## Licensing

- Use the vendor's own download page for every image. This page links nothing else, and neither should issues or pull requests here.
- **Cisco images (IOS for Dynamips, IOSv, IOU/IOL, ASAv, ...) need a licence from Cisco.** GNS3 can't provide images or licences ([GNS3 IOU docs](https://docs.gns3.com/docs/emulators/non-native-iou-for-windows-and-osx)). The legal way to run current Cisco images is [Cisco Modeling Labs](https://www.cisco.com/c/en/us/products/cloud-systems-management/modeling-labs/index.html) (CML-Free, 5 nodes, no cost; Personal and Enterprise editions are paid). Cisco licenses the images that come with CML for use **inside CML only**. Its [CML-Free docs](https://developer.cisco.com/docs/modeling-labs/2-8/cml-free/) say using them outside CML without a proper licence is prohibited, so a CML licence does not by itself cover running those images in GNS3.
- The images below are free to download. Each has its own terms (summarised in the table). Arista's vEOS-lab needs a free Arista account.

## Worked example

Upload the VyOS rolling ISO to the local compute, and look up a blank disk that GNS3 already ships:

```terraform
resource "gns3_image" "vyos" {
  compute_id = "local"
  emulator   = "qemu"
  filename   = "vyos-2026.10.07-0712-rolling-generic-amd64.iso"
  source_url = "https://github.com/vyos/vyos-nightly-build/releases/download/2026.10.07-0712-rolling/vyos-2026.10.07-0712-rolling-generic-amd64.iso"
}

# Already on every 2.2.61 compute: GNS3 puts its blank disks in the QEMU folder.
data "gns3_image" "disk" {
  emulator = "qemu"
  filename = "empty8G.qcow2"
}

output "vyos" {
  value = "${gns3_image.vyos.path} (${gns3_image.vyos.filesize} bytes, md5 ${gns3_image.vyos.md5sum})"
}

output "disk_md5" {
  value = data.gns3_image.disk.md5sum # bfd65172dea027c3fc2eb5dfa3a7c2b9 on 2.2.61
}
```

What happens on `terraform apply`:

1. The provider lists the compute's qemu images. If the ISO is already there and `md5sum` matches (or, with no `md5sum`, the downloaded file has the same MD5), it adopts the file without uploading.
2. Otherwise it downloads the ISO to a temporary file, checks it against `md5sum` when that is set, streams it to `POST /v2/computes/local/qemu/images/<filename>`, lists the images again and takes `path`, `md5sum` and `filesize` from the compute. The temporary file is deleted afterwards.
3. If a different file with that name is already on the compute, the apply fails instead of overwriting it. Import it (`terraform import gns3_image.vyos local/qemu/<filename>`) or pick another name.

Later plans:

- Changing `source_url` alone uploads nothing. Set or change `md5sum` to upload the new file over the old one.
- With `md5sum` set, a refresh that finds a different file on the compute plans an update that uploads the source again. A file deleted from the compute plans a new upload.
- `terraform destroy` removes the resource from state and warns that the file is still on the compute. GNS3 2.2 has no API to delete images (`DELETE` answers 405), so delete the file from the folder in the table above if you need the space.

To use the ISO, create a qemu template in the GNS3 GUI (or a `gns3_node` with `node_type = "qemu"` and `properties = jsonencode({ cdrom_image = gns3_image.vyos.filename, hda_disk_image = data.gns3_image.disk.filename, ram = 2048 })`; not tried against a server yet).
