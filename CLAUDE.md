# terraform-provider-gns3

Terraform provider for GNS3, built on `terraform-plugin-framework` (not SDKv2). Module `github.com/JerryBalmer1/terraform-provider-gns3`, registry address `JerryBalmer1/gns3`, version 0.2.0 (`var version` in `main.go`; GoReleaser overrides it with `-X main.version`). It targets GNS3 server 2.2.x over REST v2 and was built against the 2.2.52 docs.

## Working rules

Generic (copy to any Invoke-Build repo):

- **Stop and ask** if a probe disagrees with the docs, a task fails twice, the change touches files the prompt did not name, anything would be deleted, or a version bump would be breaking.
- **Never run `git commit`, `git push` or `git tag`.** Edit and stage only. `.claude/settings.json` blocks them with a PreToolUse hook.
- **Every task ends with the report template** (`.claude/skills/report-template/SKILL.md`).
- **Tooling gaps are reported, not worked around.** When an Invoke-Build task fails, lacks a switch or would force a raw command, name it under "Tooling gaps" instead of running the raw command. Skills: `.claude/skills/` (build-and-verify, release-prep, docs, report-template; repo-specific: probe, add-scenario).
- **Hooks:** `Invoke-Build Setup` sets `core.hooksPath=.githooks` (and `hooks.rangeTask`) once per clone, so `git push` runs `.githooks/pre-push`: a tag runs `Release`, `main` runs `Lint, Test, Gns3Range`, any other branch runs `Lint, Test`.

Repo-specific:

- **Edit and stage only.** Never commit, push, branch, tag or release. `git add` is the last git step; Jerry commits. Never run `goreleaser release`. `goreleaser check` only validates the config and is allowed.
- **manual-check-list.md is append-only.** Never renumber items. Add new ones at the end of their section. Mark a withdrawn item "(removed in 0.x.0)" and leave its number unused. Item 0.1 tracks the provider version and the exported resource and data source type names; update it in the same task as any change to either. Every item has a self-contained PowerShell block, an Expect line and a Tests line naming the Go test(s) that cover the same behaviour (`Tests: none` when there are none). An Expect you haven't seen yourself is marked `(not yet seen: needs a GNS3 server)` until Jerry confirms it.
- **Data and docs state their sources.** Client methods cite their GNS3 API docs page in a comment. Every fixture under `pkg/gns3/testdata/` starts with `_header` (`hand-written from docs, not recorded` or `recorded from GNS3 <version> on <date>`) and `_source` (the docs page URL), plus `_notes` for any change from the docs sample. Schema defaults copied from server behaviour name the page they came from.
- `docs/` is generated by tfplugindocs (apart from `docs/api-drift.md`, `docs/gns3-install.md` and `docs/images.md`, which tfplugindocs leaves alone and `validate` accepts). Never edit the generated pages by hand; change the schema descriptions, `examples/` or `templates/`, then run `make docs`.
- Don't look at or copy from NetOpsChic/terraform-provider-gns3. Design from the GNS3 server API.
- Keep changes scoped. No drive-by refactors.
- Don't commit secrets, `.tfstate`, built binaries or `dist/`.
- **Never stop a GNS3 server you did not start.** `Invoke-Build Gns3Stop` stops only the process recorded in `$env:TEMP\gns3\server.pid` by `Gns3Start` (or `TestAcc -AutoStart`); a server Jerry started from the GUI is left running, whatever port it is on. Don't `Stop-Process gns3server` or call `/v2/shutdown` by hand.
- **Provider source address.** `examples/**/*.tf` name the provider `source = "JerryBalmer1/gns3"` in `required_providers`, because that is what users write and what the dev override (`dev_overrides { "JerryBalmer1/gns3" = ... }`) matches. The Go tests (`Test*` and `TestAcc*`) keep the terraform-plugin-testing default, `registry.terraform.io/hashicorp/gns3`: `ProtoV6ProviderFactories` serves the provider in-process under the bare name `gns3`, the test configs carry no `required_providers` block, and Terraform resolves an unqualified `gns3` to `hashicorp/gns3`. No registry lookup happens in either case, so the namespace in test output means nothing.

## Client design

`gns3.Client` is version-neutral and made of `ProjectsAPI`, `NodesAPI`, `LinksAPI`, `TemplatesAPI`, `ComputesAPI`, `ImagesAPI` and `VersionAPI`, plus `APIVersion()`. `gns3.NewV2(Config)` is the only implementation (`v2Client`, Basic auth). GNS3 3.x support means adding a `v3Client` (JWT from `Config.Token`, `/v3/...`) that satisfies the same interface, plus a constructor choice in `provider.go`. Don't change the interface to suit one version. Every non-2xx response becomes `*gns3.APIError`, whose `Error()` names the method, endpoint, status and server message, then the request body sent and any response detail beyond the message. Diagnostics pass `err.Error()` through unchanged.

## Behaviour rules

- No swallowed errors. A 404 on delete counts as "already gone". A 404 on read removes the resource from state, except that a node or link in a closed project is an error (`explainMissing`).
- Computed-only attributes use `UseStateForUnknown`. When an in-place update can change one (node `ports`/`console` after `properties` or `console_type` changes, project `filename` on rename), `ModifyPlan` marks it unknown, so apply never contradicts the plan.
- After a fresh apply of any example, the plan must be empty (`TestExamples`, `TestAccExamples`).
- Node ports are read back with `GET` after create.

## Local dev loop

```powershell
Set-Location C:\__Code\terraform-provider-gns3
go install .
$bin = go env GOBIN
if (-not $bin) { $bin = Join-Path (go env GOPATH) 'bin' }
$rc = Join-Path $env:APPDATA 'terraform.rc'
if (Test-Path $rc) { Copy-Item $rc "$rc.bak" -Force }
@"
provider_installation {
  dev_overrides {
    "JerryBalmer1/gns3" = "$($bin -replace '\\', '/')"
  }
  direct {}
}
"@ | Set-Content -Path $rc -Encoding ascii
```

On Linux or macOS the same block goes in `~/.terraformrc`. With the override in place, run `terraform plan` without `init`. `terraform init` and `terraform providers mirror` both go to the registry and fail until the provider is published; `terraform providers schema -json` uses the override. To test without touching the real file, set `$env:TF_CLI_CONFIG_FILE` to a scratch copy.

## Checks before staging

```powershell
go build ./...
go vet ./...
$env:GOTOOLCHAIN = 'go1.25.8'; go run honnef.co/go/tools/cmd/staticcheck@v0.7.0 ./...; Remove-Item Env:GOTOOLCHAIN
gofmt -l .            # must print nothing
go test ./... -count=1
go run github.com/hashicorp/terraform-plugin-docs/cmd/tfplugindocs generate --provider-name gns3
go run github.com/hashicorp/terraform-plugin-docs/cmd/tfplugindocs validate --provider-name gns3
```

staticcheck v0.7.0 can't read export data from Go 1.27 (the local toolchain), so it runs with `GOTOOLCHAIN=go1.25.8` (the `go.mod` version) set for that one command; the `Lint` task and `make lint` do the same.

`make` isn't installed on Jerry's Windows machine. The `GNUmakefile` targets wrap these same commands (see README "Make targets"), and so do the `.build.ps1` tasks: `Invoke-Build` (Build, Lint, Test) and `Invoke-Build Docs`. Provider unit tests need `terraform` on `PATH`.

Acceptance tests and manual-check-list section 1 need a GNS3 server: `Invoke-Build TestAcc -AutoStart` starts one with its own config under `$env:TEMP\gns3` and stops it afterwards; `Invoke-Build Checklist -Item 1.2` runs one check-list item in a fresh pwsh. Fixtures under `pkg/gns3/testdata` are recorded from a live server; when an endpoint changes, re-record that fixture rather than editing its response by hand.

## Scenario tests

`Invoke-Build Gns3Range` (or `-Scenario <name>`) runs each scenario against a live server. The server is the one already answering on `-Gns3Host`/`-Gns3Port`, or one started the way `Gns3Start` does and stopped afterwards. For each scenario it runs `terraform init -input=false -upgrade`, fails the scenario without apply or destroy when `terraform state list` shows resources left from an earlier run ("stale state from a previous run; destroy it first"), then `apply -auto-approve`, `terraform output -json` and `checks.ps1`, then `destroy -auto-approve`, which runs whenever init succeeded, even after a failed apply or failed checks. It prints a summary table and fails if any scenario failed.

```
test/scenarios/<name>/
  scenario.json   { "name", "description", "requires": ["server"] or ["server","image"] }
  main.tf         a real root module: source "JerryBalmer1/gns3", version "0.2.0", empty provider block
  checks.ps1      param(-Server <base URL>, -Outputs <hashtable: output name -> value>); calls the
                  GNS3 v2 API with Invoke-RestMethod and throws a clear message on any mismatch
  README.md       what it builds, what checks.ps1 verifies, what the GNS3 GUI shows
test/images/      files generated at run time for "image" scenarios; only .gitkeep is tracked
```

- **Two modes.** `Gns3Range` points `TF_CLI_CONFIG_FILE` at its own CLI config, so Jerry's `terraform.rc` never applies.
  - **Published (default):** the config is `direct {}` only, so scenarios run the release on the Registry. A scenario fails unless `.terraform.lock.hcl` locks `registry.terraform.io/jerrybalmer1/gns3` at the pinned version. This proves what users get; the pre-push hook runs it for `main`.
  - **`-Dev`:** `go build`s this checkout to `$env:TEMP\gns3\dev-provider`, adds `dev_overrides { "JerryBalmer1/gns3" = <that dir> }` before `direct {}`, skips the lock-file assert and prints `DEV BUILD` in the summary header. This proves unreleased code; `Release` runs it, because the version being tagged is not on the Registry yet.
  Never use a filesystem mirror.
- `requires: "image"` makes `Gns3Range` write `test/images/scenario-dummy.img` before init. Its bytes never change, because GNS3 2.2 can't delete images and `gns3_image` refuses to upload over a different file of the same name.
- In `checks.ps1`, unroll list responses (`Invoke-RestMethod ... | ForEach-Object { $_ }`): pwsh 7 writes a JSON array to the pipeline as one object.
- **Adding a scenario.** When asked to add a scenario for a resource, attribute or behaviour not already covered, first read the provider schema (`internal/provider/<name>_resource.go` or `_data_source.go`) and its page under `docs/`. If what the scenario should assert is still unclear, stop and ask rather than invent expected values.
